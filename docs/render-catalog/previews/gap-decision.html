2A new inbox row is inserted for a validated forecast.updated event, and no weather_cards row exists for the place_id. The INSERT creates a card using the place fields; forecast.updatedAt supplies updated_at and JSON.stringify(event.forecast) supplies forecast. Commit, then map nonzero result.rowCount to APPLIED.
3A new forecast event conflicts on place_id and the stored weather_cards.updated_at is null, or incoming event.forecast.updatedAt is strictly greater than the stored updated_at. The SQL conflict update is allowed and sets name, latitude, longitude, updated_at, and forecast from the incoming event. Commit, then map nonzero result.rowCount to APPLIED.
4A new forecast event conflicts on place_id, stored updated_at is nonnull, and incoming event.forecast.updatedAt is equal to or earlier than the stored value. The strict greater-than WHERE predicate prevents the card update, leaving its fields unchanged. The inbox row is still committed; result.rowCount zero maps to OLDER_OR_EQUAL.
5A new inbox row is inserted for a validated place.requested event, taking the helper's else branch. Upsert place id, name, and coordinates. The conflict update list does not assign forecast. Commit; the helper maps result.rowCount zero to OLDER_OR_EQUAL and nonzero to APPLIED.

After selection: execution and outcomes

The rejection insert is awaited before its offset commit; if it rejects, that later commit is not reached. pool.connect occurs before applyEvent's try, so its rejection bypasses the helper rollback catch and release finally. Errors caught inside the helper try cause an awaited ROLLBACK attempt and rethrow if rollback resolves; the acquired client is released in finally. Because consumeMessage awaits applyEvent outside its parse and validation catch, a rejected helper prevents the later offset commit. The captured handler shows no local catch for commitOffsets failures.
